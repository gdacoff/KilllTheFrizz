## 1. Резюме для руководства

В рамках фазы 7.10.9.1 проведена строгая инспекция исходного кода и байткода реализации `CollisionThrottler` в `KilllTheFrizz`.

### Ключевые результаты аудита:
1. **Устранено расхождение в калибровке порога движения:**
   - В исходной спецификации прототипа был задокументирован `STATIONARY_VELOCITY_SQR = 0.0009` ($0.03\text{ blocks/tick}$).
   - В плотных загонах для скота взаимное отталкивание при столкновениях сообщает сущностям микроимпульсы порядка $\sim 0.05\text{ blocks/tick}$ ($v^2 \approx 0.0025 > 0.0009$), из-за чего 100% коров обходили троттлер.
   - Порог был перекалиброван на `STATIONARY_VELOCITY_SQR = 0.04` ($0.20\text{ blocks/tick}$ — стандартная скорость ходьбы сущности в Minecraft).
   - Верификация байткода (`javap`) подтверждает, что скомпилированный класс `CollisionThrottler.class` и production-тестовый JAR содержат `ldc2_w 0.04d`.
   - `PHASE_7_10_5_IMPLEMENTATION.md` содержал устаревший фрагмент кода, тогда как `PHASE_7_10_CAMPAIGN_FINAL_REPORT.md` и фактический исходный код корректно указывают `v² > 0.04`.
2. **Корректность математики расслоения:**
   - Формула `Math.floorMod((long) entity.tickCount + entity.getId(), 2) == 0` математически гарантирует разбиение последовательных ID сущностей и последовательных тиков на чередующиеся 50%-ные группы без переполнения 32-битного целого.
3. **Конфигурационное стробирование и изоляция бенчмарков:**
   - `CollisionThrottler.shouldPushEntities` проверяет три условия:
     1. `KtfConfig.getEffectiveCommon().enabled()` (главный переключатель).
     2. `!KtfConfig.isAutoDisabled()` (защита монитора замедления).
     3. `KtfConfig.getEffectiveServer().sleepingEnabled()` (серверный переключатель, управляемый пресетом).
   - В пресете `OFF` `sleepingEnabled == false`, что обеспечивает 100% выполнение ванильных коллизий на полной частоте.
   - В пресете `SAFE` `sleepingEnabled == true`, что активирует `CollisionThrottler`.
   - Нагрузка 1 (250 чистых коров) изолирует `CollisionThrottler` от `VillagerBrainThrottler`, тогда как нагрузка 2 (смешанная популяция) оценивает совместный синергетический эффект обеих функций.

## 3. Математический анализ и анализ расслоения во время выполнения

### 3.1 Выражение каденции
```java
long phase = (long) entity.tickCount + entity.getId();
return Math.floorMod(phase, STAGGER_PERIOD) == 0;
```

### 3.2 Верификация инвариантов:
1. **Безопасность переполнения:** `entity.tickCount` — 32-битное целое. Приведение `(long) entity.tickCount` повышает сложение `(long) tickCount + id` до 64-битной целочисленной арифметики. Взятие по модулю 2 не может вызвать зацикливание или искажение знака.
2. **Обработка отрицательных значений:** Java-метод `Math.floorMod(x, 2)` даёт строго неотрицательные результаты $[0, 1]$, даже если `phase < 0` (в отличие от оператора `%`, который возвращает $[-1, 0]$ для отрицательных делимых).
3. **Пространственное распределение по ID сущностей:**
   Поскольку ID сущностей генерируются последовательно (`AtomicInteger` в `Entity.nextEntityId()`), соседние сущности во вновь заспавненной группе имеют чередующиеся ID ($k, k+1, k+2, \dots$).
   На любом заданном тике $t$:
   $$\text{phase}_k = t + k, \quad \text{phase}_{k+1} = t + k + 1$$
   Ровно одно из них чётное, а другое нечётное. Следовательно, ровно 50% плотного кластера выполняет `pushEntities()`, а оставшиеся 50% пропускают.
4. **Временное чередование:**
   На тике $t+1$ оцениваемое разбиение полностью меняется:
   $$\text{phase}_k(t+1) = t + 1 + k = \text{phase}_k(t) + 1$$
   Ни одна сущность не пропускает проверки коллизий более чем на 1 последовательный тик (максимальная пауза 50 мс).

## 4. Аудит конфигурационного стробирования и изоляции пресетов

### 4.1 Код реализации
```java
if (!KtfConfig.getEffectiveCommon().enabled() || KtfConfig.isAutoDisabled()
        || !KtfConfig.getEffectiveServer().sleepingEnabled()) {
    return true;
}
```

### 4.2 Сравнение состояний конфигурации

| Функция / Настройка | Пресет: `OFF` | Пресет: `SAFE` | Примечания |
|:---|:---:|:---:|:---|
| **Глобальный главный переключатель (`enabled`)** | `true` (файл) | `true` (файл) | Не зависит от пресета |
| **`sleepingEnabled`** | `false` | `true` | Управляет SleepingEntities и CollisionThrottler |
| **`CollisionThrottler`** | **ОТКЛЮЧЁН (100% частота)** | **ВКЛЮЧЁН (каденция 10 Гц)** | В OFF обходит троттлинг |
| **`VillagerBrainThrottler`** | `false` | `true` | Троттлит мозг жителей в SAFE |
| **`squeezerEnabled`** | `false` | `true` | Дедупликация памяти data attachment |
| **`autoDisabled`** | Отслеживается | Отслеживается | Fail-open при деградации TPS сервера |

### 4.3 Оценка изоляции бенчмарков
* **Нагрузка 1 (250 коров в загоне 5x5):**
  - Мобы: чистый скот. Жители отсутствуют $\to$ `VillagerBrainThrottler` не срабатывает.
  - Позиция игрока: расстояние 10 блоков (внутри `sleepRadius = 48/64`) $\to$ коровы бодрствуют; `SleepingEntities` не пропускает их AI.
  - **Вердикт:** Нагрузка 1 обеспечивает **чистое, изолированное измерение `CollisionThrottler`**.
* **Нагрузка 2 (смешанная 200: 40 жителей + 160 животных):**
  - Жители выполняют `VillagerBrainThrottler` в режиме SAFE.
  - Коровы/свиньи/овцы выполняют `CollisionThrottler` в режиме SAFE.
  - **Вердикт:** Нагрузка 2 представляет собой **композитный многофункциональный бенчмарк**, оценивающий совместный синергетический эффект оптимизации AI и коллизий.
