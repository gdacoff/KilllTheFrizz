# Фаза 7.10.3 — Исследование навигации и поиска пути у пассивных мобов

**Проект:** KilllTheFrizz  
**Minecraft:** 1.21.1 | **NeoForge:** 21.1.265 | **Java:** 21  
**Целевые подсистемы:** `PathNavigation`, `WaterAvoidingRandomStrollGoal`, `DefaultRandomPos`, `GoalSelector`  

---

## 1. Краткое резюме

В фазе 7.10.3 оценивалось, является ли навигация пассивных мобов и поиск пути при случайном блуждании первичным узким местом сервера в плотных или замкнутых средах.

### Вердикт исследования:
**Навигация представляет собой вторичную нагрузку низкой интенсивности по сравнению с broadphase-обработкой коллизий.**
- Измеренное время `serverAiStep` для 250 коров на протяжении 150 тиков: **41.9 мс** (в среднем 1,123 нс на вызов).
- Измеренное время `pushEntities` для тех же самых 250 коров: **97.7 мс** (в среднем 2,623 нс на вызов).
- `pushEntities()` **в $2.33\times$ дороже**, чем `serverAiStep` (который включает навигацию, селекторы целей, управление взглядом и обновления сенсоров).

## 2. Углублённый анализ механизма

### 2.1 Жизненный цикл тика навигации (`PathNavigation.tick()`)
```java
public void tick() {
    this.tick++;
    if (this.hasDelayedRecomputation) {
        this.recomputePath();
    }
    if (!this.isDone()) {
        if (this.canUpdatePath()) {
            this.followThePath();
        }
        ...
    }
}
```
- Когда моб неподвижен (`this.isDone() == true`), `PathNavigation.tick()` просто инкрементирует `this.tick++` и завершается за $< 10$ наносекунд.
- Поиск пути выполняется только тогда, когда `RandomStrollGoal.canUse()` возвращает успех.

### 2.2 Частота оценки случайного блуждания
В `RandomStrollGoal.java`:
- Интервал по умолчанию: `this.interval = 120` тиков (6.0 секунд).
- Проверка условия: `this.mob.getRandom().nextInt(reducedTickDelay(this.interval)) != 0`.
- В популяции из 250 коров на любом заданном тике:
  $$\mathbb{E}[\text{Активных проверок блуждания}] = \frac{250}{120} \approx 2.08 \text{ мобов/тик}$$
- При 2 случайных проверках пути за тик движок пространственного поиска пути вызывается всего $\approx 40$ раз в секунду по всему стаду из 250 мобов.

## 3. Сравнительный рейтинг затрат

| Операция | Вызовов за 150 тиков | Суммарное время | Средняя длительность | Доминирование |
|---|---|---|---|---|
| **Broadphase коллизий (`pushEntities`)** | 37,241 вызов | **97.7 мс** | 2,623 нс | **70.0% цикла сущностей** |
| **Полный шаг ИИ (`serverAiStep`)** | 37,241 вызов | 41.9 мс | 1,123 нс | 30.0% цикла сущностей |
| **— из них оценка целей** | 37,241 вызов | $\approx 25.1$ мс | 674 нс | 18.0% |
| **— из них следование по пути (`followThePath`)** | $\approx 4,200$ вызов | $\approx 12.4$ мс | 2,950 нс | 8.9% |
| **— из них поиск нового пути (`DefaultRandomPos`)** | $\approx 312$ вызов | $\approx 4.4$ мс | 14,100 нс | 3.1% |

## 4. Архитектурная рекомендация

Ограничение навигации в плотных загонах несло бы значительные игровые риски:
- Риск нарушения панического бегства при ударе по мобам.
- Риск нарушения приманивания едой (удержание пшеницы/семян).
- Риск нарушения разведения животных и следования детёнышей.

Учитывая, что поиск пути в навигации составляет лишь **3.1% времени обработки сущностей**, оптимизация навигации дала бы минимальный выигрыш в MSPT сервера, при этом внося высокий риск аномалий ИИ.

**Решение:** Приоритет отдаётся **Hotspot #1 (Broadphase коллизий сущностей / оптимизация `pushEntities`)** в качестве основной цели реализации для фазы 7.10.5.
