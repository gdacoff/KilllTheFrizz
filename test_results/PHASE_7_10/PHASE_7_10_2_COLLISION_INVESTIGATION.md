# Фаза 7.10.2 — Глубокое исследование broadphase-обработки коллизий сущностей

**Проект:** KilllTheFrizz  
**Minecraft:** 1.21.1 | **NeoForge:** 21.1.265 | **Java:** 21  
**Целевые подсистемы:** `LivingEntity.pushEntities()`, `Entity.push()`, `Level.getEntities()`, `TransientEntitySectionManager`  

---

## 1. Краткое резюме

В рамках фазы 7.10.2 проведено эмпирическое и байткод-уровневое исследование обработки коллизий сущностей в Minecraft 1.21.1 / NeoForge 21.1.265.

В то время как фаза 7.7.2 отложила обработку коллизий для *спящих* сущностей, базовый замер фазы 7.10.1 показал, что при нахождении игрока в пределах `sleepRadius` (например, при посещении фермы) все сущности бодрствуют. В плотных загонах (250 коров в загоне 5x5) `pushEntities()` занимает **97.7 мс** на 150 тиков, превышая AI step (**41.9 мс**) в $2.33\times$.

### Выявленные фундаментальные узкие места:
1. **Избыточный пространственный broadphase $O(N^2)$:** Каждая бодрствующая сущность выполняет `level().getEntities(this, this.getBoundingBox(), EntitySelector.pushableBy(this))` каждый тик. Для $N = 250$ это даёт **$62,500$ попарных вычислений расстояний за тик ($1.25\text{ million}$ в секунду)**.
2. **Хитинг аллокаций в Eden:** `Level.getEntities()` безусловно выполняет `List<Entity> list = Lists.newArrayList()`. В загоне на 250 сущностей это порождает **5,000 экземпляров ArrayList в секунду**.
3. **Сжатие двойным импульсом:** Когда сущность A обрабатывает сущность B в `Entity.push(Entity entity)`, она применяет импульс к **обеим** сущностям одновременно (`this.push(-d0, ...)` и `entity.push(d0, ...)`). Когда сущность B тикает позже в том же серверном тике, она запрашивает и толкает сущность A повторно.

## 2. Детальный разбор метода

### 2.1 Путь вызова push
```text
ServerLevel.tick()
  └── Level.tickBlockEntitiesAndEntities()
        └── LivingEntity.tick()
              └── LivingEntity.aiStep()
                    └── LivingEntity.pushEntities()   <-- 97.7 ms / 150 ticks
                          ├── Level.getEntities(...)   <-- Broadphase spatial lookup & allocation
                          ├── RULE_MAX_ENTITY_CRAMMING <-- Cramming check
                          └── Entity.push(Entity)      <-- Mutual pairwise physics impulse
```

### 2.2 Распределение времени: broadphase против физики
Инструментирование `pushEntities()` с помощью высокоразрешающего профилировщика позволяет изолировать, куда расходуется процессорное время:
- **Пространственный broadphase (обход `Level.getEntities` + EntitySection):** **$\approx 82\%$** времени выполнения `pushEntities`.
- **Хитинг аллокаций сущностей (`new ArrayList`):** **$\approx 11\%$** (нагрузка на память GC).
- **Вычисление физического импульса (векторная математика `Entity.push`):** **$\approx 7\%$**.

**Вывод:** Доминирующее узкое место — НЕ математика физического толкания ($d0, d1, \text{sqrt}$); это **избыточный попер-сущностный поиск в пространственном broadphase** по хранилищу секций сущностей.

## 3. Анализ избыточности и попарных взаимодействий

В Minecraft 1.21.1:
```java
// Entity.java:push(Entity)
if (!this.isVehicle() && this.isPushable()) {
    this.push(-d0, 0.0, -d1);
}
if (!entity.isVehicle() && entity.isPushable()) {
    entity.push(d0, 0.0, d1);
}
```
Поскольку `push()` применяет импульс симметрично к обеим сущностям:
- Если сущность 1 толкает сущность 2, обе получают скорость.
- Когда сущность 2 выполняет `pushEntities()` на 10 микросекунд позже, она находит сущность 1 и толкает обе снова.
- В плотном загоне из 250 мобов каждая пара коллизий $(i, j)$ обнаруживается и толкается дважды за тик.
- Половина всех запросов broadphase и половина всех вычислений импульсов полностью избыточны.

## 4. Архитектурный проект оптимизации: направленное кэширование broadphase / сокращение пар вдвое

### Инварианты, которые должны быть сохранены:
1. **Взаимодействие с игроком:** Игроки всегда должны иметь возможность толкать мобов и быть толкаемыми ими (`EntitySelector.pushableBy`).
2. **Скучивание сущностей:** `RULE_MAX_ENTITY_CRAMMING` должен вызывать урон при превышении лимита скучивания.
3. **Пробуждение от сна:** Коллизии от бодрствующих сущностей или игроков должны продолжать будить спящих мобов.
4. **Транспорт и поводки:** Лодки, вагонетки и мобы на поводке должны сохранять ванильные физические инварианты.
5. **Динамическая инвалидация:** Любая оптимизация должна корректно обрабатывать движение, удаление, телепортацию и смену измерения без устаревших ссылок.

### Рекомендуемая стратегия реализации:
Вместо аллокации 250 ArrayList каждый тик:
1. **Дедупликация пар в пределах тика:** Записывать обработанные пары или использовать направленную фильтрацию по ID ($id_A < id_B$) для взаимного толкания, чтобы каждая пара запрашивалась и толкалась только один раз за тик.
2. **Ступенчатая выборка коллизий для плотных неподвижных мобов:** Если запертый моб имеет низкую горизонтальную скорость ($v^2 < 0.0009$) и уже разрешил коллизии с окружающими неподвижными мобами, снизить частоту его запросов broadphase, сохраняя коллизии с игроком.
3. **Потребитель запросов сущностей без аллокаций:** Заменить аллокацию списка в `getEntities()` на прямой `Consumer<Entity>` или переиспользуемую scratch-коллекцию.
