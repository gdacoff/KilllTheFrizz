## 1. Главные технические выводы аудита

В ходе аудита горячего пути Phase 7.1 выявлены **4 критических скрытых дефекта производительности**, которые объясняют, почему мод не давал ощутимого снижения MSPT на реальном сервере:

```mermaid
graph TD
    A["Вызов Mob.serverAiStep()"] --> B{"wasSleeping == false?"}
    B -->|ДА (Моб бодрствует)| C["ДЕФЕКТ 1: Сквозное падение в Stage 4 каждый тик!"]
    C --> D["hasNearbyAlivePlayer() каждые 50ms"]
    C --> E["ДЕФЕКТ 3: id.toString() -> 5,000 аллокаций строк/сек"]
    C --> F["ДЕФЕКТ 4: recordRejection() -> LOCK XADD на шине CPU"]
    
    A --> G["ДЕФЕКТ 2: isForceAwake(mob)"]
    G --> H["ConcurrentHashMap + UUID hashing + Memory Leak при смерти"]
```

### Дефект 1: Сквозной оверхед на бодрствующих мобах
Условие `if (wasSleeping && !isEvalTick) return true;` на строке 98 `IdleChecker.java` защищает от лишней работы **только спящих мобов**. Если моб бодрствует (`wasSleeping == false`), он **каждый тик** проваливается в дорогостоящий блок Stage 4: ищет игроков через `hasNearbyAlivePlayer()`, проверяет списки и аллоцирует строки. На сервере с 200 бодрствующими мобами менеджер сна сам становится заметным потребителем CPU.

### Дефект 2: Скрытая утечка памяти в `WAKE_TIMERS`
Статическая карта `ConcurrentHashMap<UUID, Long>` удаляет записи только тогда, когда живой моб опрашивается после истечения таймера. Если моб погиб, сгорел или чанк выгрузился, запись `(UUID, Long)` остаётся в памяти JVM **навсегда**. При многочасовом аптайме сервера карта бесконечно разрастается.

### Дефект 3: Шторм аллокаций строк `id.toString()`
В `IdleChecker.java:127` для каждого опрашиваемого моба вызывается `ResourceLocation.toString()`, создающий новый объект `String` и массив байтов в куче. При 250 мобах в загоне это генерирует **до 300,000 временных строк в минуту**, провоцируя спайки сборщика мусора (GC pressure).

### Дефект 4: Бессмысленные атомарные блокировки `AtomicLong`
Все 15 диагностических счётчиков `REJECTION_REASONS` обновляются через `incrementAndGet()`. В однопоточном серверном цикле тиканья сущностей это вызывает инструкции `LOCK XADD` на системной шине процессора, тормозя L1/L2 кэш ядра без какой-либо необходимости.
