## 2. Углублённый аудит: взаимодействие `MobMixin` и `LivingEntityMixin`

Ядро оптимизации фазы 7.7.2 опирается на кросс-миксинную координацию между `MobMixin` (`serverAiStep`) и `LivingEntityMixin` (`pushEntities`).

```
                              LivingEntity.aiStep()
                                       │
                  ┌────────────────────┴────────────────────┐
                  │                                         │
                  ▼                                         ▼
         Mob.serverAiStep()                    LivingEntity.pushEntities()
                  │                                         │
                  ▼                                         ▼
            MobMixin.java                         LivingEntityMixin.java
                  │                                         │
         IdleChecker.shouldSleep()                          │
                  │                                         │
                  ├─► Returns TRUE (Sleep):                 ├─► Checks SleepStateAccess:
                  │     • ktf$wasSleeping = true            │     • ktf$isSleeping() == true
                  │     • noActionTime++                    │     • Evaluate cramming (& 15 == 0)
                  │     • ci.cancel()                       │     • ci.cancel()
                  │                                         │
                  └─► Returns FALSE (Awake):                └─► ktf$isSleeping() == false
                        • ktf$wasSleeping = false                 • Vanilla pushEntities() runs
                        • Normal AI executes                      • KtfProfiler timing active
```

### 2.1 Петля обратной связи пробуждения
Критический вопрос, исследованный в ходе данного аудита: **может ли спящий моб когда-либо застрять навсегда из-за пропуска `pushEntities()`?**

**Ответ: математически и архитектурно невозможно.**
1. `pushEntities()` — это *исходящее действие* (сущность отталкивает *других*).
2. Быть оттолкнутым внешней сущностью (игроком, взрывом или бодрствующим мобом) — это *входящий стимул*, применяемый через `other.doPush(this)` или `this.push(vx, vy, vz)`.
3. В Minecraft 1.21.1 `doPush` добавляет импульс непосредственно в `this.getDeltaMovement()`.
4. На следующем тике ($1 \text{ tick} = 50 \text{ ms}$ максимальной задержки):
   - `MobMixin` выполняет `serverAiStep()`.
   - `IdleChecker.shouldSleep()` запускает **Стадию 2 (дешёвые проверки пробуждения)**:
     ```java
     if (mob.getDeltaMovement().horizontalDistanceSqr() > serverCfg.maxIdleVelocitySqr()) {
         return false; // VELOCITY WAKEUP
     }
     ```
   - Поскольку `doPush` придаёт $\Delta v \approx 0.05 \text{ blocks/tick}$, а $\text{maxIdleVelocity} = 0.03$ ($\text{maxIdleVelocitySqr} = 0.0009$), то $(0.05)^2 = 0.0025 > 0.0009$.
   - Стадия 2 срабатывает немедленно, устанавливая `ktf$wasSleeping = false`.
   - Сущность полностью бодрствует, выполняя полный AI и обычный `pushEntities()` на этом же самом тике.

### 2.2 Повторный вход в сон
Как только внешний импульс затухает за счёт трения о землю (демпфирование $0.546 \times 0.91 \approx 0.496$ за тик):
- В течение 2–3 тиков скорость падает ниже $0.03$.
- Если рядом нет игрока, навигация неактивна и урон не был получен, моб плавно возвращается в сон на следующем тике со сдвинутой оценкой.

## 3. Сравнительный аудит скучивания: Vanilla vs KillTheFrizz

Одним из конкретных требований фазы 7.7.3 была проверка модифицированной реализации скучивания на соответствие ванильному поведению и документирование различий в тайминге или частоте нанесения урона.

### 3.1 Таблица механистического сравнения

| Свойство | Vanilla Minecraft 1.21.1 | KillTheFrizz спящий моб | KillTheFrizz бодрствующий моб |
|---|---|---|---|
| **Частота оценки** | Каждый тик (20 Гц) | Каждые 16 тиков (`((tickCount + id) & 15) == 0`) | Каждый тик (20 Гц) |
| **Вероятность за оценку**| 25% случайно (`random.nextInt(4) == 0`) | 100% детерминированно при перенаселении | 25% случайно (`random.nextInt(4) == 0`) |
| **Величина урона** | 6.0F generic cramming | 6.0F generic cramming | 6.0F generic cramming |
| **Ожидаемое время до первого урона**| $E[T] = 4 \text{ ticks} = 0.20 \text{ s}$ | $E[T] = 8 \text{ ticks} = 0.40 \text{ s}$ (диапазон 1–16) | $E[T] = 4 \text{ ticks} = 0.20 \text{ s}$ |
| **Состояние после урона** | Сохраняет бодрствующее состояние | **Пробуждается немедленно (`hurtTime = 10`)** | Сохраняет бодрствующее состояние |
| **Последующие тики скучивания** | 25% за тик | **Выполняет ванильные проверки 25% за тик** | 25% за тик |
| **Взаимные толчки сущностей** | `doPush` вызывается для всех сущностей | Обходится (нулевая взаимная скорость) | `doPush` вызывается для всех сущностей |
| **Накладные расходы CPU в загоне на 250 мобов** | 1,947 нс/моб каждый тик | ~0 нс на 15/16 тиков | 1,947 нс/моб |

### 3.2 Анализ динамических переходов
Обратите внимание на ключевой гибридный переход:
1. Когда 30 коров спавнятся в яму 1x1, они изначально попадают под оценку скучивания.
2. На своём соответствующем сдвинутом тике (равномерно распределённом по 16 тикам) перенаселённая корова получает 6.0F урона от скучивания.
3. Получение урона устанавливает `hurtTime = 10`.
4. На самом следующем тике `MobMixin` вызывает `IdleChecker.shouldSleep()`.
5. Стадия 2 оценивает: `if (mob.hurtTime > 0 || mob.isOnFire()) return false;`.
6. **Повреждённый моб пробуждается немедленно!**
7. После пробуждения моб больше не спит (`ktf$wasSleeping == false`).
8. На всех последующих тиках `LivingEntityMixin` позволяет **полному ванильному методу `pushEntities()`** выполняться каждый тик с ванильной случайной вероятностью 25%!
9. Как только лишние коровы задохнутся и количество сущностей упадёт до 24 (`maxEntityCramming`), урон от скучивания прекращается, скорость затухает, и выжившие 24 коровы возвращаются в сон.

**Эмпирический результат:** в TM-07A 30 коров в шахте 1x1 были сведены к **ровно 24 коровам** в течение 5 секунд, что идентично ванильному равновесию.

## 4. Матрица верификации инвариантов

### 4.1 Контракт деспавна мобов (`noActionTime`)
- В ванильном Minecraft `Mob.serverAiStep()` начинается с `this.noActionTime++`.
- При отмене AI (`ci.cancel()`) ванильный инкремент пропускается.
- `MobMixin` явно сохраняет этот контракт:
  ```java
  if (sleep) {
      mob.setNoActionTime(mob.getNoActionTime() + 1);
      KtfStats.recordSkippedAiTick();
      ci.cancel();
      return;
  }
  ```
- Результат: спящие мобы инкрементируют `noActionTime` каждый тик, что обеспечивает полную аутентичность правил естественного деспавна (деспавн через 600 тиков, если игрок > 32 блоков; мгновенный, если > 128 блоков).

### 4.2 Размножение и рост детёнышей
- Кормление пшеницей устанавливает `InLove: 600`.
- Стадия 4 вычисляет `animal.isInLove()` и возвращает `false`, предотвращая сон мобов в режиме любви.
- Родители успешно перемещаются, спариваются и порождают сущности детёнышей.
- Стадия 4 вычисляет `animal.isBaby()` и возвращает `false`, гарантируя, что детёныши животных остаются бодрствующими и подвижными на протяжении всего цикла роста.

### 4.3 Безопасность транспорта и поводка
- `mob.isPassenger()`, `mob.isVehicle()` и `mob.isLeashed()` размещены в **Стадии 2 (Дешёвые проверки пробуждения)**.
- Стадия 2 выполняется каждый тик без ожидания интервалов.
- Сущности в лодках, вагонетках или на поводках никогда не входят в сон, что обеспечивает плавную физику транспорта, клиент-серверную интерполяцию и натяжение поводка.

### 4.4 Перемещения между измерениями и сохранение мира
- Транзиентное состояние памяти: `ktf$wasSleeping` не записывается в NBT-файлы чанков.
- Сохранение мира (`save-all flush`) и загрузка заново чисто пересчитывают состояние сна на первом тике сущности.
- Кулдаун портала Нижнего мира и таймеры перехода тикают без прерываний.
