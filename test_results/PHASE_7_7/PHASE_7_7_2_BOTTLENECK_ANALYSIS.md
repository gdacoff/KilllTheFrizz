## 1. Резюме для руководства

На шаге 2 фазы 7.7.2 мы выполнили 12 изолированных итераций рантайм-бенчмарка на 4 различных нагрузках по сущностям (250 коров в загоне, 100 разбросанных коров, 100 жителей и 200 смешанных мобов на пастбище 24x24), сравнивая `Preset.OFF` с `Preset.SAFE` с использованием наносекундных метрик `KtfProfiler` высокого разрешения и телеметрии профилировщика Spark.

### Ключевые измеренные выводы:
1. **Реалистичная фермерская нагрузка (200 смешанных мобов) подтверждает эффективность SleepingEntities:**
   - Доля спящих достигла **34.7%** (69,291 пропущенный вызов за 1,305 тиков).
   - Медианный MSPT улучшился с **1.93 мс (OFF) до 1.87 мс (SAFE)**, при этом P95 улучшился с **2.50 мс до 2.30 мс** (снижение P95 MSPT на 8.0%).
2. **Плотный загон (250 коров в 16x16) выявляет каскад коллизионных толчков:**
   - Доля спящих осталась на уровне **1.49%** (4,724 пропущенных вызова).
   - На `pushEntities()` пришлось **61.1% времени обработки сущностей** (1,947 нс/моб против 1,239 нс/моб для `serverAiStep()`).
   - Взаимные физические толчки сообщают импульс $0.05 \text{ blocks/tick}$, который превышает `maxIdleVelocity` ($0.03$), вызывая непрерывные взаимные пробуждения между соприкасающимися мобами.
3. **ИИ жителей по-прежнему определяется вычислениями Brain/Schedule:**
   - На `serverAiStep()` приходится **98.7% времени тика** (29,119 нс/моб против 325 нс для `pushEntities()`).
   - Жители безопасно занесены в чёрный список в `Preset.SAFE` во избежание регрессий расписания POI.

## 3. Исследование первопричины: каскад коллизий в загоне

### 3.1 Механика `LivingEntity.pushEntities()`

В ванильном Minecraft 1.21.1 `LivingEntity.aiStep()` вызывает `this.pushEntities()` на каждом тике каждой сущности:

```java
// net.minecraft.world.entity.LivingEntity
protected void pushEntities() {
    List<Entity> list = this.level().getEntities(this, this.getBoundingBox(), EntitySelector.pushable(this));
    if (!list.isEmpty()) {
        int i = this.level().getGameRules().getInt(GameRules.RULE_MAX_ENTITY_CRAMMING);
        if (i > 0 && list.size() > i - 1 && this.random.nextInt(4) == 0) {
            int j = 0;
            for (Entity entity : list) {
                if (!entity.isPassenger()) {
                    j++;
                }
            }
            if (j > i - 1) {
                this.hurt(this.damageSources().cramming(), 6.0F);
            }
        }
        for (Entity entity : list) {
            this.doPush(entity);
        }
    }
}
```

Когда сущность $A$ сталкивается с сущностью $B$, `doPush` вычисляет:

```java
// net.minecraft.world.entity.Entity
protected void doPush(Entity other) {
    double d0 = other.getX() - this.getX();
    double d1 = other.getZ() - this.getZ();
    double d2 = Mth.absMax(d0, d1);
    if (d2 >= 0.009999999776482582) {
        d2 = Math.sqrt(d2);
        d0 /= d2;
        d1 /= d2;
        double d3 = 1.0 / d2;
        if (d3 > 1.0) d3 = 1.0;
        d0 *= d3 * 0.05000000074505806;
        d1 *= d3 * 0.05000000074505806;
        d0 *= (double)(1.0F - this.pushthrough);
        d1 *= (double)(1.0F - this.pushthrough);
        this.push(-d0, 0.0, -d1);
        other.push(d0, 0.0, d1);
    }
}
```

### 3.2 Математический конфликт с `IdleChecker`
- Импульс скорости, прикладываемый `doPush`: $\Delta v \approx 0.05 \text{ blocks/tick}$.
- `IdleChecker.maxIdleVelocity`: $0.03 \text{ blocks/tick}$ ($\text{maxIdleVelocitySqr} = 0.0009$).
- Поскольку $0.05 > 0.03$:
  1. На тике $N$ мобы $A$ и $B$ находятся в физическом контакте.
  2. Моб $A$ выполняет `pushEntities()`, вызывая `doPush(Mob B)`. Моб $B$ получает скорость $+0.05$.
  3. Моб $B$ выполняет `pushEntities()`, вызывая `doPush(Mob A)`. Моб $A$ получает скорость $+0.05$.
  4. На тике $N+1$ `MobMixin` вызывает `IdleChecker.shouldSleep()`.
  5. Стадия 2 вычисляет `mob.getDeltaMovement().lengthSqr()`. Величина составляет $\approx (0.05)^2 = 0.0025 > 0.0009$.
  6. Стадия 2 не проходит: `shouldSleep()` возвращает `false`. Оба моба остаются бодрствующими.
  7. Оба моба выполняют полный ИИ, снова вызывают `pushEntities()` и бесконечно поддерживают цикл.

Это объясняет, почему в загоне 16x16 (высокая плотность) сон был искусственно ограничен до **1.49%**, тогда как в загоне 24x24 (более низкая плотность) доля сна сразу подскочила до **34.7%**.

## 5. Архитектурная спецификация оптимизации шага 4

### 5.1 Предлагаемый дизайн: отложенная обработка толкания для спящих мобов
Когда моб спит (`ktf$wasSleeping == true`):
1. **Импульсы толкания:** у спящего моба отсутствует намерение автономного перемещения. Он не должен рассылать импульсы толкания соседним неподвижным спящим мобам.
2. **Взаимодействие с игроком / бодрствующим мобом:** если игрок или бодрствующий моб входит в спящего моба, `pushEntities()` бодрствующей сущности выполняется штатно, вызывая `doPush(sleepingMob)`. Это придаёт ускорение спящему мобу, из-за чего на следующем тике его `deltaMovement.lengthSqr() > 0.0009`, и он немедленно просыпается!
3. **Ванильный max entity cramming:**
   Если `maxEntityCramming > 0`, сущности по-прежнему должны получать урон от удушения, если более $K$ сущностей занимают один и тот же координатный бокс.
   Чтобы предотвратить эксплуатацию cramming при нулевых накладных расходах на тик:
   - Если `maxEntityCramming <= 0`, спящие мобы отменяют `pushEntities()` в 100% случаев.
   - Если `maxEntityCramming > 0`, спящие мобы выполняют оценку cramming только на своём запланированном тике оценки (`((tickCount + id) & 15) == 0`) или каждые 20 тиков, пропуская `doPush()`.

### 5.2 План реализации
1. Экспортировать состояние `isSleeping()` из `MobMixin` в `LivingEntity` через внутренний интерфейс (`SleepStateAccess`).
2. В `LivingEntityMixin`:
   - Внедрить `@At("HEAD")` в `pushEntities(CallbackInfo ci)` с `cancellable = true`.
   - Если `(Object) this instanceof SleepStateAccess sleep && sleep.ktf$isSleeping()`:
     - Проверить cramming, если `maxEntityCramming > 0`, на периодических тиках.
     - `ci.cancel();`
3. Проверить с помощью модульных тестов:
   - Бодрствующий моб вызывает `pushEntities()`.
   - Спящий моб отменяет `pushEntities()`.
   - Внешний импульс будит спящего моба.
4. Запустить набор бенчмарков для измерения прироста MSPT и изменения доли сна.
